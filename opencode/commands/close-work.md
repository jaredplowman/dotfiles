---
description: Choose a feat, fix, or chore commit, squash commits onto the target branch, push the branch, and remove its worktree
subagent: false
---

Close the current work in this order: commit any uncommitted changes, squash commits onto the target branch, push to origin, then remove the linked worktree. Additional context: $ARGUMENTS

1. Identify the current Git worktree with `git rev-parse --show-toplevel` and `git worktree list --porcelain`. If the session is in the main worktree, ask which linked worktree to close; never remove the main worktree. Read the applicable `AGENTS.md` instructions for the selected worktree and inspect its branch, `git status --short --branch`, and staged/unstaged/untracked changes. Do not guess which worktree or branch the user means. Stop if its HEAD is detached or the branch cannot be identified; ask the user how to proceed.
2. Ask the user via the `question` tool to choose the commit type (`commit-feat`, `commit-fix`, or `commit-chore`) if there are uncommitted changes, and ask which target branch to squash onto (unless already clear from context or `$ARGUMENTS`). Ask for any desired commit wording if needed. These correspond to the existing global commit commands; follow their commit subject/body style. Show the planned subject and the files to be included before committing. If there are unrelated or ambiguous changes, ask what to include rather than staging everything blindly. Do not amend or create an empty commit; if the worktree is already clean, proceed directly to the squash step (or ask whether to proceed with pushing and closing if there is nothing to commit or squash).
3. If there are uncommitted changes to commit, stage only the approved changes, review `git diff --cached` and status, then create ONE commit with `git commit -m "<type>: <concise descriptive subject>" -m "<short descriptive body>"` (subject at most 120 characters, type `feat`, `fix`, or `chore`). Do not invoke the slash command inside a shell. If the selected global commit command has additional formatting rules, honor them; its "Do NOT push" instruction applies to that command in isolation, not this closing workflow.
4. Load and follow the `squash` skill (`use skill tool with id: "squash"`) to squash the branch's commits onto the target branch before pushing. By default, summarize using only the commit messages and descriptions (unless the user requested `--code` / code inspection). If there is only 1 commit between the target branch and `HEAD`, keep it as-is without rewriting unless the user asked to rewrite it.
5. Before pushing, verify the exact branch and that no uncommitted changes remain in the target worktree. Verify that `origin` exists and inspect the branch's upstream. If it tracks a different remote or branch, or `origin/<branch>` already exists with divergent history, stop and ask rather than overwriting anything. Push the current branch to `origin` using `git push -u origin <branch>` (normal push only; never force push). If the push fails, stop and leave the worktree intact. Verify the push succeeded before proceeding.
6. Only after a successful push and a clean worktree, move the current OpenCode session out of the linked worktree using `execute` with `tools.opencode.session_move({ directory: "<main-worktree-directory>" })`. Preserve the session's relative subdirectory under the main worktree when it exists; otherwise use the main worktree root. If the session is already elsewhere, do not move it. Then remove ONLY the selected linked worktree with `execute` and `tools.opencode.worktree_remove({ directory: "<exact-linked-worktree-root>" })`, without `force`. Do not delete the branch or discard changes. If moving the session or removing the worktree fails, report the failure and leave the worktree intact; do not use recursive deletion as a fallback.
7. Report the final squashed commit (or that there was none), pushed branch, and whether the worktree was removed. Do not run a build solely to close work; follow any project-specific verification policy.
